# Backend agent guide

This file applies to everything under `backend/` and supplements the repository-root `AGENTS.md`.
The implementation and tests are authoritative; the guides under `docs/` explain the intended
architecture and must remain synchronized with behavior.

## Read before editing

Choose the smallest relevant set, starting with `README.md` and `docs/README.md`:

- application boundaries and dependency rules: `docs/architecture.md`;
- local setup, configuration, launcher, migrations, and operations: `docs/development.md`;
- test design and commands: `docs/testing.md`;
- routes, authentication, status codes, and payloads: `docs/api.md`;
- persistence and relationships: `docs/data-model.md`;
- pure engine behavior: `docs/simulation-engine.md`;
- scenario schema and authored runtime content: `docs/scenario-authoring.md` and
  `docs/authored-content.md`;
- consequential architecture decisions: `docs/adr/README.md`.

Trace a behavior end to end before changing it: API route -> application service -> persistence or
pure domain package -> focused tests -> user-facing documentation.

## Hard architecture boundaries

- `app/api` owns HTTP transport, authentication dependencies, serialization, and mapping domain
  errors to HTTP. Routes obtain request-scoped sessions but do not commit, duplicate business rules,
  or call engine internals directly.
- `app/auth`, `app/classes`, `app/scenarios`, `app/simulations`, and `app/results` own application
  workflows. A mutating service owns the complete transaction and commits domain and audit records
  atomically; read-only services never commit.
- `app/simulations` is the stateful integration owner for persisted runs, optimistic versions,
  idempotency, the engine, and authored content. Do not confuse it with the pure `app/simulation`
  package.
- `app/simulation` is deterministic and side-effect free. It must not import FastAPI, SQLAlchemy,
  database models, application services, authored content, wall-clock time, or process entropy.
  Randomness is injected through the existing random-source abstraction, and state remains
  serializable through `state_codec.py`.
- `app/authored_content` is pure policy over definitions and plain projections. It must not import
  persistence, `SimulationState`, engine transitions, or randomness, and it never mutates a run.
- `app/scenarios` owns validated, immutable numbered revisions. Published revisions and historical
  snapshots are never edited in place.
- `app/batch` runs scenarios in memory and must not access or migrate the database.
- `app/db` owns ORM and database infrastructure, not domain workflows. Alembic—not `create_all()`—is
  the schema history for persistent databases.

See the package matrix in `docs/architecture.md` before introducing any cross-package import. If a
change truly alters a boundary, update that matrix and add or supersede an ADR.

## Backend implementation conventions

- Target Python 3.13 and 100 columns. Ruff configuration in `pyproject.toml` is authoritative.
- Use current type syntax and match the surrounding immutable dataclass/Pydantic patterns. Keep API
  models explicit rather than returning unreviewed ORM or internal state shapes.
- Use timezone-aware UTC datetimes, deterministic ordering, and fixed seeds. Persist every input
  needed to replay a historical turn; never recalculate history with today's engine behavior.
- Keep transactions short. Use `flush()` only when generated values are needed and commit once in
  the owning service. On an expected integrity conflict, roll back before reusing the session.
- Preserve optimistic-version and idempotency semantics in run commands. A retry with the same key
  and payload may replay; reuse with different content must remain a conflict.
- Authentication uses opaque tokens whose hashes—not plaintext values—are stored. Maintain role and
  ownership checks, generic unauthorized/not-found behavior where used to prevent disclosure, and
  secure cookie policy. Never place credentials or sensitive authored content in logs or errors.
- Validate scenario definitions with `ScenarioDefinition`; do not hand-index unvalidated external
  JSON. Student projections must continue to exclude professor-only content and answer keys.
- Settings are read at process import/startup from exported environment variables; `.env.example`
  is documentation, not an automatically loaded dotenv file.

## Database and migration changes

Any ORM schema change requires a reviewed Alembic revision and migration tests. Keep the migration
chain linear, use descriptive revision metadata and named constraints/indexes, and treat shared
migrations as immutable. Review autogenerated migrations manually; they cannot infer rename,
backfill, portability, or data-preservation intent.

Test both a clean upgrade and representative existing data. Exercise downgrade when it can be
truthful and safe; document irreversible destructive behavior rather than pretending data can be
recovered. Do not edit `alembic_version`, blindly stamp a database, hand-edit persisted JSON, or use
`Base.metadata.create_all()` to repair schema drift. Follow `docs/development.md` and
`docs/sqlite-operations.md` for backup and operational checks.

## Tests and required checks

Place tests in `tests/test_<domain>.py` beside the closest ownership boundary. Keep fixtures local,
use `tmp_path` for SQLite, close sessions and dispose engines, and create only required data. Cover
pure rules at the engine layer, transaction/idempotency behavior at the service layer, and auth,
roles, statuses, and error shapes at the API layer.

From `backend/`, iterate with a focused node and finish with:

```bash
uv sync --locked
uv run ruff format --check .
uv run ruff check .
uv run pytest
```

From the repository root, also run:

```bash
uv run --project backend python scripts/check_docs.py
```

For migration work, additionally run `uv run alembic heads` (exactly one head), upgrade a clean
temporary database to `head`, and test representative upgrade/rollback behavior. For scenario or
engine changes, validate affected examples and run representative fixed-seed batches in addition to
the focused and full test suites.

## Change-coupling checklist

- Route, request, response, auth, status, or error change: update `docs/api.md`, API tests, and the
  corresponding frontend adapter/tests when applicable.
- Setting or CLI change: update `.env.example`, `docs/development.md`, launcher/config tests, and
  deployment guidance where operational behavior changes.
- ORM or migration change: update `docs/data-model.md`, migration tests, and SQLite operational or
  deployment guidance as needed.
- Scenario or authored-content change: update schema/model tests, validated examples,
  `docs/scenario-authoring.md`, and `docs/authored-content.md`.
- Simulation rule, state, result, or replay change: update fixed-seed tests,
  `docs/simulation-engine.md`, compatibility/version handling, and batch coverage.
- Package responsibility or durable design change: update `docs/architecture.md` and add/supersede
  an ADR when the rationale should outlive the patch.

Before handoff, inspect the entire diff for accidental database files, scenario answer leakage,
secrets, nondeterminism, missing migrations, and documentation drift.
