# HTTP API

## Base URL and interactive schema

During local development the default base URL is `http://127.0.0.1:8000`. Application routes
use the `/api` prefix. OpenAPI documentation is available at `/docs` and the raw schema at
`/openapi.json`.

JSON request models reject unknown fields. Timestamps are ISO 8601 strings. Identifiers are
opaque strings and must not be parsed by clients.

## Authentication

Authentication uses the `pm_sim_session` HTTP-only cookie. Browser requests must retain and
send cookies. JavaScript must never read or persist the session value.

```http
POST /api/auth/login
Content-Type: application/json

{"username":"professor","password":"example-password"}
```

The successful response is a user object:

```json
{"id":"...","username":"professor","role":"professor"}
```

Relevant endpoints:

| Method | Path | Access | Purpose |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | Public | Create a browser session. |
| `POST` | `/api/auth/logout` | Any | Revoke the current session and clear its cookie. |
| `GET` | `/api/auth/me` | Authenticated | Restore the current frontend session. |
| `PUT` | `/api/auth/password` | Authenticated | Change the password and revoke existing sessions. |

Professors are created from the local CLI, not through a public registration endpoint. Students
are imported by a professor or associated with a class by username.

## Status and error conventions

Successful deletion-style operations generally return `204 No Content`. Validation failures
generated by FastAPI return `422`. Application errors have the shape:

```json
{"detail":"human-readable explanation"}
```

Common statuses are:

- `400 Bad Request`: invalid lifecycle operation or decision;
- `401 Unauthorized`: no valid session;
- `403 Forbidden`: authenticated but missing the professor role;
- `404 Not Found`: missing resource or a resource hidden by ownership rules;
- `409 Conflict`: stale simulation version, archived state, or an import conflict;
- `422 Unprocessable Entity`: malformed request fields.

Clients should branch on the status code. The `detail` text is suitable for display but is not
a stable machine-readable code.

## Scenario endpoints

All scenario-authoring endpoints require a professor.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/scenarios/validate` | Validate and normalize without saving. |
| `POST` | `/api/scenarios` | Create a scenario and draft revision 1. |
| `GET` | `/api/scenarios` | List the professor's active scenarios. |
| `GET` | `/api/scenarios/{scenario_id}` | List all owned revisions. |
| `POST` | `/api/scenarios/{scenario_id}/revisions` | Append a draft revision. |
| `POST` | `/api/scenarios/{scenario_id}/revisions/{number}/publish` | Publish a revision. |
| `POST` | `/api/scenarios/{scenario_id}/archive` | Archive without deleting history. |

A revision response contains `id`, `scenario_id`, `revision_number`, `schema_version`, `status`,
`definition`, `created_at`, and `published_at`. The frontend should retain the revision **ID** when assigning
or starting simulations; the revision number is only meaningful within its scenario.

## Class endpoints

Except for `available-scenarios`, class endpoints require a professor and enforce ownership.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/classes` | Create a class. |
| `GET` | `/api/classes` | List active owned classes. |
| `PATCH` | `/api/classes/{class_id}` | Rename a class. |
| `POST` | `/api/classes/{class_id}/archive` | Archive a class. |
| `GET` | `/api/classes/{class_id}/students` | List enrolled students. |
| `POST` | `/api/classes/{class_id}/students/import` | Create and enroll up to 100 students. |
| `POST` | `/api/classes/{class_id}/students` | Enroll an existing student by username. |
| `DELETE` | `/api/classes/{class_id}/students/{student_id}` | Remove a membership. |
| `PUT` | `/api/classes/{class_id}/students/{student_id}/password` | Reset a student's password. |
| `GET` | `/api/classes/{class_id}/scenarios` | List assigned revisions. |
| `POST` | `/api/classes/{class_id}/scenarios` | Assign a published owned revision. |
| `DELETE` | `/api/classes/{class_id}/scenarios/{revision_id}` | Remove an assignment. |
| `GET` | `/api/classes/available-scenarios` | List revisions available to the current user. |

`GET /api/classes/available-scenarios` is the student's entry point for choosing a scenario. Its
items contain `id`, `class_id`, `class_name`, `revision_number`, and the complete `definition`.
The same revision can appear more than once when it is assigned through multiple classes.

## Simulation endpoints

All simulation endpoints require authentication and expose only runs owned by the current user.
Run detail responses include the scenario's `employee_types` so the weekly decision screen can
offer valid hiring choices without duplicating scenario data in the frontend.

They also include an `authored_content` student projection. This projection contains only
currently delivered, student-visible definitions and presentation state. Professor-only entries,
undelivered definitions, definition digests, replay metadata, and hidden facts are never included.

### Start and retrieve a run

```http
POST /api/simulations
Content-Type: application/json

{"scenario_revision_id":"...","class_id":"...","seed":12345}
```

`class_id` is optional at the schema level. Students normally provide it so the service can
verify enrollment and scenario availability. A run response includes the current `version` and
`state`; retain both in frontend state.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/simulations` | Start a run. |
| `GET` | `/api/simulations` | List the current user's runs. |
| `GET` | `/api/simulations/{run_id}` | Fetch current state and version. |
| `GET` | `/api/simulations/{run_id}/turns` | Fetch visible decision/event history. |
| `POST` | `/api/simulations/{run_id}/turns` | Complete one week. |
| `POST` | `/api/simulations/{run_id}/submit` | Finish and score a run. |

### Complete a weekly turn

Every turn request requires a unique `Idempotency-Key` header and the version last read by the
client:

```http
POST /api/simulations/{run_id}/turns
Idempotency-Key: 9bfabef4-frontend-generated-value
Content-Type: application/json

{
  "expected_version": 1,
  "allocation": {
    "development": 55,
    "unit_testing": 20,
    "bug_fixing": 15,
    "integration_testing": 10
  },
  "hires": [],
  "dismiss_employee_ids": [],
  "overtime_hours_per_employee": 0,
  "meeting_hours_per_employee": 0,
  "training_hours_per_employee": 0
}
```

Allocation values are percentages from 0 through 100 and must satisfy the domain allocation
rules. On success, replace the frontend's cached run with the returned `run`. The `replayed`
field is `true` when a retry returned an already committed turn.

Generate one idempotency key when the user submits a decision and retain it until that request
has succeeded or has been intentionally abandoned. Do **not** generate a new key merely because
the network timed out. On `409`, refetch the run, show that the state changed elsewhere, and ask
the user to review the decision against the new version.

Weekly completion is structurally blocked when a required authored delivery at the canonical
`before_week:N` checkpoint remains incomplete. The `409` response identifies the blocking
delivery; clients must answer or acknowledge it rather than resubmitting a differently shaped
weekly decision. After the engine commits week N, `after_week:N` deliveries are resolved and are
associated with that persisted turn. `run_started` and `before_week` deliveries have no turn;
`run_finished` deliveries are also unassociated. An effect has a turn only when its delivery does.

### Answer or acknowledge authored content

```http
POST /api/simulations/{run_id}/content/{delivery_id}/answer
Idempotency-Key: answer-uuid
Content-Type: application/json

{"expected_version":2,"answer":{"option_id":"quality"}}
```

Use `/acknowledge` with `{"expected_version":2}` for fragments and events. Questions accept
exactly one successful answer; acknowledgement cannot bypass a question. Both commands use the
run's optimistic `expected_version` and increment it on success. A stale expected version is
`409 Conflict`. Retrying the same key with the same canonical request returns the original result
without another response or effect. Reusing a key with a different canonical request digest is a
`409` idempotency conflict. Canonicalization normalizes the command kind, delivery, expected
version, and answer (including stable ordering for multi-choice answers) before hashing.

Answers are **authored responses / learning interactions**, never score contributions. Supported
effects are presentation-only (`show_message`, presentation flags, and presentation themes).
State-changing effects and scored questions are rejected during scenario validation.

### Submit a run

```json
{"expected_version": 8}
```

Submission also uses optimistic concurrency. The returned run has its final status, finish
timestamp, and `final_result`.

## Professor results and audits

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/classes/{class_id}/results` | List student run summaries and final results. |
| `GET` | `/api/classes/{class_id}/results/{run_id}` | Retrieve complete state and turn audit. |
| `GET` | `/api/audit?limit=50&offset=0` | Retrieve the professor's administrative actions. |

The detailed professor run audit contains information intentionally hidden from the student
during play. It must only appear in professor screens. Its `content_audit` object contains:

- immutable deliveries with sequence ordinal, canonical checkpoint, visibility and
  `hidden_from_students`, definition snapshot/digest, status/timestamps, and optional turn ID/week;
- authored responses with command kind, normalized answer, response version, request digest, and
  a one-way digest of the idempotency key;
- applied presentation effects with payload/index, before/after projection digests, timestamp,
  and optional turn association;
- aggregate `digest_status` (`verified` or `diverged`) and structured replay `divergences`, each
  reporting category, record, expected value, and actual value.

The projection digests cover canonical student presentation state, not simulation state or score.
Professor replay is read-only and does not synthesize historical deliveries, responses, or effects.
